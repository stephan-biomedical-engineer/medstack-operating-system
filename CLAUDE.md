# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`MedPlatform` — an undergraduate engineering thesis (TCC) proposing a reusable, layered Yocto Project reference architecture for building multiple classes of embedded **medical devices** (not a single specific device). The proof of concept is an EEG acquisition system with Asymmetric Multiprocessing (AMP: Cortex-A35 Linux + Cortex-M4 real-time core) and an HMI display, targeting both QEMU x86-64 (simulation) and STM32MP257 (physical hardware).

Yocto release: **Scarthgap (5.0 LTS)**. Build orchestration: Siemens **KAS**.

The PoC's analogue front-end is the **TI ADS1299** (8-channel, 24-bit biopotential AFE, SPI + `DRDY`), and it reaches the platform by **four declared links**, selected by `MED_EEG_LINK`: `simulated` (no converter), `amp` (converter on the Cortex-M33, Linux never touches it — the product topology and the one that carries the IEC 62304 §5.3 partitioning argument), `spi` (converter on the host's SPI6 with `DRDY` as a real interrupt) and `usb` (converter behind an MCP2210 USB-SPI bridge, which cannot deliver an interrupt to a host at all). The last two are driven by Linux through **kernel IIO drivers this project owns**, in an adjunct layer; `amp` is driven by firmware over `rpmsg`. They are *not* clinically equivalent, which is why `acquisition.link` is written into every session's metadata: on `usb` a sample's timestamp is when the host was told, one bus frame and one wakeup after the conversion — an error of phase, not of date, and one no arithmetic downstream can undo. `docs/implementation_plan_ads1299.md` and `docs/implementation_plan_iio_afe.md` are the two plans, and both now carry an implementation record.

`docs/implementation_plan_mac.md` is a second current plan: it records the AppArmor-vs-SELinux decision for `MedOS` (outcome: **AppArmor**, via `meta-security`), the file-by-file changes it needs, and — importantly — that it is sequenced *after* the first green `kas build`, not before. Nothing in it is implemented yet; the build it waited on is now green, so it is unblocked.

`docs/implementation_plan_rauc.md` is the third current plan, and — unlike the other two — it is **implemented and validated**; its §8 records the measured results. The A/B update path now works on QEMU: `rauc.service` starts, enumerates both slots, identifies the booted one, and `rauc install` verifies a signed verity bundle against the device keyring and writes the inactive slot. Two decisions in it bind future work: `bootloader=` is now `MED_BOOTLOADER`, a per-machine variable substituted like `MED_EEG_DRIVER` (the distro layer must not name a bootloader), and validation is deliberately capped below a real GRUB A/B switch, because `boot-attempts` is `uboot`/`barebox`-only — so GRUB fallback on QEMU would exercise a different mechanism than the STM32MP257 ships. Say "the A/B policy is validated on QEMU"; for the STM32MP257, install, activation and the slot switch itself are validated on hardware as of 2026-08-31 (`implementation_plan_uboot_ab.md` §8) and the **fallback on a failing slot is not** — that one still needs fault injection, and until it has seen the failure it looks for it is a claim, not a check.

`docs/implementation_plan_luks.md` is the fourth plan and, like the third, is **implemented and validated** — its §8 records the measured results. `/data` is a real LUKS2 volume, provisioned on first boot by `med-data-provision.service`, and `MED_EEG_REQUIRE_ENCRYPTION` is now `"true"` on QEMU: `MedicalStorage` requires `/data`'s `dm/uuid` to start with `CRYPT-`, so the acquisition service running at all *is* the assertion. Key custody is `MED_DATA_KEY_SOURCE`, defaulting to `tpm2` so a target that forgets fails loudly rather than shipping something that looks encrypted and is not; `tpm2` itself refuses to provision rather than half-existing. **Where** a development key may live is now a second, separate variable pair (`MED_KEY_STORE_DEV`/`MED_KEY_STORE_FSTYPE`) answered per machine by `meta-med-bsp`, because "a partition no update writes to" is a partition table and therefore a board fact — the ESP on EFI machines, `med-boot` on the STM32MP2. Its §9 also records that `tpm2` is **not reachable** in the current layer set (meta-tpm ships only software emulators; there is no OP-TEE fTPM recipe), so custody is development-grade on *both* targets, not just on the simulation one.

Two things there are worth knowing before touching that code. The safeguard in `med-data-provision.sh` distinguishes "never provisioned" from "LUKS header damaged" — which produce identical symptoms — by keying on the pristine ext4 label wic writes, and refuses anything else rather than reformatting over patient records; it has been exercised by zeroing the header, and it holds. And a key has to survive an A/B slot switch: a key on the rootfs would be destroyed by the first *successful* update, leaving the device unable to decrypt its own records, which is why the development key lives on the ESP. That is the same hazard §7.3 describes for TPM PCR sealing, and §7.3 is still unevaluated.

That work also turned up a rule worth carrying: **in this repository, "it builds and boots" is not evidence about the update path.** Six defects were found, and five of them failed nothing — a `system.conf` missing `check-purpose` (every field update rejected, with the correct certificate as the cause), a bundle `compatible` string that silently disagreed with the device's, `WKS_FILE ?=` in the distro conf that never won against `qemux86-64.conf` because `bitbake.conf` includes the machine conf before the distro conf (so the A/B GPT layout was never in the image at all), A/B slots that came out different sizes because wic treats `--size` as a minimum and applies a 1.3 overhead factor only to a partition with a `--source`, and an `/etc/fstab` naming `/dev/sda1` for `/boot` because wic's `--ondisk` defaults to `sda` while QEMU presents virtio. Inspect produced artefacts (`sfdisk -l` the `.wic`, read the installed config) rather than trusting a green build.

`make check` is the runtime acceptance suite: it boots the QEMU image, runs 23 assertions over the serial console, and exits non-zero on failure.

The 23rd, `acq-sample-rate`, is worth knowing about because of what it caught. The suite used to report 22/22 on an image whose acquisition delivered **94 of a configured 250 samples per second per channel** whenever the HMI was attached: the publish path blocked (`accept4` without `SOCK_NONBLOCK`, then a blocking `write`), so a viewer that could not keep up throttled acquisition, and the record ended up claiming a rate it did not contain. Every one of the 22 measured *state* - active, no restarts, socket published - and the service was perfectly active while losing 62% of its samples. **Measuring state is not measuring function.** Fixed (`RESULTS.md` §3): the accepted channel is non-blocking, `send` returns the new `Status::WouldBlock`, and the service counts the frames a viewer missed into the `AcquisitionStopped` audit record. A viewer may lose data; the record may not.

Two things in how that was found are the transferable part. It was **latent and pre-existing** - at 10 frames/s the viewer kept up - and raising the frame rate from 10 to 17.9 Hz exposed it, which is the second time in one session that fixing one defect revealed the next (the `QB_MEM` OOM was the first). Treat finishing a fix as the moment to look for what it was hiding. And the new assertion was **fault-injected before being believed**: reverting the single `SOCK_NONBLOCK` flag and rebuilding gives 22/23 with `acq-sample-rate` as the only failure, which proves both that it sees the defect and that the others cannot. Run it after any change that could affect runtime behaviour — it is the only thing in this repository that catches a regression a build cannot. When adding an assertion, remember what fault injection taught this suite: `acq-active` used `systemctl is-active` and passed a crash-looping service, because a `Type=simple` unit with `Restart=on-failure` is briefly active on every retry. An assertion that has never seen the failure it looks for is a claim, not a check.

And the corollary, learned when the suite caught the front-end work: **when `make check` finds a defect a build could have found, the fix includes moving the check into the build.** An inline `# comment` after a value in `eeg.conf` becomes part of the value — `MedicalConfiguration::parse` takes everything after the `=` — so `afe.gain = 24  # PGA` is not a number, the safety envelope stops the service, and six assertions fail at once. The platform behaved correctly (a calibration value it cannot parse must never be guessed at) and the parser was deliberately left alone, but finding it cost a full image build and a QEMU boot. `do_seal_configuration` now refuses both an inline comment in a value and a surviving `@NAME@` placeholder, in a second, naming the line — and both guards were fault-injected before being believed.

`docs/RESULTS.md` is the measured evidence — the experimental half of the thesis. It is the place to look before claiming anything about this platform's behaviour, and the place to record a new measurement. Every number carries the command that produced it and an explicit statement of what it does **not** mean; its §9 lists what has not been measured, so an absence is not read as a result. Two things there are easy to overstate and are deliberately framed against that: the reuse figure is reported as "the platform both device classes inherit is 206 packages, the EEG's device-specific delta is 3" rather than as a similarity percentage (the tomograph installs no device application, so its delta is zero by construction), and the A/B update result covers the update *policy*, not bootloader integration.

`docs/BRINGUP_STM32MP2.md` is the engineering record of the port to the physical target — every defect, its real cause, and what proved the fix, plus the host-side disk work the port forced. Its §9 is the hardware record, one subsection per bench session (§9.1–§9.7 the first boot, 2026-08-18; §9.10 the first `rauc install`, 2026-08-30), and its §11 is the transferable part: fifteen rules earned the expensive way, including "a documented assumption about third-party behaviour is debt", "a generic name over machine-specific content is the standard disguise for layer bleeding", "a defect hidden behind a refusal is still a defect", "inspecting the artefact does not substitute for powering the board", "a device name is always a race, never a fact", and — added by the update-path work — "the factory state is a state, and somebody has to create it", "two programs with the same name are not the same program", and "`rauc info` passing says nothing about `rauc install`".

`docs/implementation_plan_uboot_ab.md` is the fifth plan and is **implemented and validated on hardware, except the fallback** (2026-08-31: a freshly flashed card boots with `rauc.slot=A` and `Activated: rootfs.0 (A)`; then `rauc install` → `BOOT_ORDER=B A` → reboot → `Booted from: rootfs.1 (B)` with slot A still `good` and still in the order — no `fw_setenv` at any point. Only the fallback on a failing slot is unmeasured, and its §8 says so) — it closes boot-slot selection, `rauc.slot=` on the cmdline, the missing factory `BOOT_ORDER` and A/B fallback with one piece: a `bootcmd` shipped inside a U-Boot environment image that wic writes into the `u-boot-env` partition, so a freshly flashed card is already in the factory state and nothing is corrected at runtime. Two decisions in it bind the work: the vendor's `extlinux.conf` is left untouched **as the rescue path**, so a lost or corrupt environment degrades to exactly today's behaviour (booting slot A) instead of to `root=PARTUUID=` empty and a panic — which is why the tempting alternative, making `extlinux.conf` slot-agnostic with `root=PARTUUID=${med_root}`, is rejected even though U-Boot really does expand env vars inside `APPEND` (this repo has proof: the BSP's `console=${console},${baudrate}` reaches the kernel as `console=ttySTM0,115200`). And attempt counters are capped at 9, because U-Boot's `setexpr` parses hex while `test` parses decimal — they agree only below 10, and RAUC writes the counter with `%x`. Its §7.1 names the one thing that needs a serial console before any code is written: which variables give the MMC device and the `med-boot` partition number.

`docs/BRINGUP_HMI_QEMU.md` and `docs/BRINGUP_HMI_STM32MP2.md` are the two records of getting the operator display to run — the first on QEMU, the second on the board, where **the HMI finally rendered on an HDMI monitor** (2026-08-27: `NRestarts=0`, 1.099 s of CPU in 2 min 22 s, and a DRM plane of 1030x633, which is the QML window plus the shell's decoration). Four defects stood between the compositor and the screen, and each fix moved the failure rather than removing it — **73 ms** (no seat, fixed by the `seatd` unit) → **6 s** (`/dev/galcore` is `crw------- root root` and weston runs as uid 1000) → **up and invisible** (weston's 300 s idle timeout, which never resets on a board with no input devices) → **image**. The last one is the instructive one: with the CRTC active, the mode programmed, `transfer_error=0`, `fifo_underrun_error=0` and a clean `dmesg`, `1920x1080` produced nothing and `1280x720` worked. It is not pixel rate — 148.5 MHz works while 119.0 MHz fails; what separates them is CEA-861 timings against PC (CVT/DMT) ones. **Three of those fixes exist only as `chmod`/`vi` on a running card and do not survive a reboot**: a udev rule for `galcore` (`meta-med-bsp`), `idle-time=0` in a `weston.ini` of our own (`meta-med-distro`), and a pinned CEA mode (`meta-med-bsp`, via a per-machine hook). On QEMU the same suite of problems produced a different pair, and **both are now fixed**: `SystemCallFilter=mincore` (applied and validated on hardware) and `QB_MEM`, whose poky default of 256 MiB makes weston OOM-loop — now `QB_MEM:qemux86-64 = "-m 1024"` in `meta-med-bsp`, beside `QB_FSINFO` and `QB_KERNEL_ROOT`, because the RAM of a virtual machine is a machine fact. That one was specified in `BRINGUP_HMI_QEMU.md` §9 and left unimplemented until it charged again: it makes `make check` report the first fifteen assertions passing and the rest as "no response from the guest", with nothing failed, because the suite clears the HMI at 30 s and the OOM lands at 150. Note how it stayed hidden — while an earlier defect killed the acquisition service, the HMI never got far enough to consume the memory, so fixing that defect is what exposed this one. A defect masked by another defect is the same shape as "a defect hidden behind a refusal". The remaining gap is the suite's 30 s horizon (`BRINGUP_HMI_QEMU.md` §9), which is still open.

`docs/implementation_plan_iio_afe.md` is the sixth plan and is **implemented, minus everything that needs hardware** — its §13 draws that line exactly, and it is the section to read before claiming anything about the front-end. It supersedes the ADS1299 plan's "Ligação B": the USB mode of the analogue front-end is **kernel IIO**, not a userspace bridge over `/dev/hidraw*`.

What exists: `meta-custom/meta-med-afe-ads1299`, an adjunct layer holding two out-of-tree kernel modules, a udev rule and the hat's devicetree overlay; an `iio` driver in the MedFramework that speaks the IIO ABI with `open`/`read`/`poll` and text files and adds **no** dependency (no `libiio` — the framework still has exactly two, which is a property of the thesis); a fixed-layout `amp::ControlMessage` so front-end settings reach a producer with the same discipline as the sample frame; and `MED_EEG_LINK` selecting all of it.

What was measured: the 6.9→6.6 backport of `ti-ads1298.c` cost **zero lines of API drift** (every interface it uses exists in both kernels this repo builds — verified by reading the trees, then by compiling); both modules **compile and link clean for arm64 against the board's real kernel** (`linux-stm32mp` 6.6.129, `W=1`, no warnings, `modpost` resolving everything, correct HID/SPI/OF aliases); 80 host checks of the new framework behaviour pass; both images build; and `make check` is **23/23** on QEMU, which is a regression check rather than an acquisition measurement (the driver in use there is `simulated`). What was **not** done: no module was ever loaded, no sample was ever acquired, and no datasheet constant was checked.

Three decisions bind future work. The AFE driver is **not written from scratch** — the ADS1298 is the ECG sibling of the ADS1299 in the same family, so the work is a backport plus an adaptation, on maintainer-reviewed code, which is what keeps it out of the SOUP category (IEC 62304 §3.29). The drivers live in an **adjunct layer**, outside the four `MedStack` layers: the reuse metric is computed over the `meta-med-*` layers, and quarantining a front-end's kernel code keeps that measurement clean while turning "a new AFE costs one adjunct layer and three variables, and zero lines in the four platform layers" into a result. And `CONFIG_IIO_HRTIMER_TRIGGER` was deliberately **not** added despite the plan asking for it: it drags in `IIO_SW_TRIGGER` → `IIO_CONFIGFS` → `CONFIGFS_FS` on a read-only rootfs, for a trigger nothing would bind, because the AFE driver carries its own timer for the link that has no interrupt.

That plan also carries a recorded method error worth imitating: the first version concluded "write both drivers from scratch" from a search scoped to this repository's own kernel tree, never asking whether a sibling chip had a driver anywhere.

Two things in the front-end drivers are debt and are labelled as such in the source. **Every datasheet constant is unverified** — the ADS1299 register map and the MCP2210 opcodes, offsets and VID/PID are marked `[SBAS499?]` / `[DS20005176?]` and grouped at the top of each file so that checking them is one pass; until that pass happens they are exactly what `BRINGUP_STM32MP2.md` §11 rule 1 means by debt. And the claim that a specific `hid_device_id` table beats `hid-generic` is **read in the kernel source** (`hid_generic_match` declines any device another registered driver matches, `hid-generic.c:37-57`) and not observed; `KERNEL_MODULE_AUTOLOAD` is there because that reading says the remaining race is one of load order.

`docs/implementation_plan_afe_bench.md` is the seventh plan and **nothing in it has been executed** — it is the bench routine for the day the hardware arrives, and it is what pays the two debts the paragraph above names. Nine phases, each with a numeric criterion, a fault injection and a place to record the number; Phase 0 (check every `[SBAS499?]` / `[DS20005176?]`) blocks every measurement in the others, because the later phases *interpret* silicon using those constants. Two structural facts about it are worth knowing before touching the front-end. **Phase 8 is split in two**, `8-A` sweeping the ADS1299's datasheet and `8-B` sweeping the MCP2210's, because the bridge lives in the kernel's trust domain, has the less verified datasheet of the two and **no cross-reference at all** (the AFE has a mainline sibling driver as an oracle; the bridge has nothing), and because most of its features were deliberately *not* implemented — so a large part of that sweep is **negative tests**, of which "the NVRAM is byte-for-byte unchanged after a whole session" is the important one: a driver that wrote it by accident would change a fielded device's VID/PID, on a soldered part, so its own driver would no longer match. And **8-B does not depend on the converter**, so it runs with an evaluation board and a jumper before the analogue board exists, while §13.1 — the host-side unit tests of the transfer state machine — needs no hardware at all.

Three things from writing that plan bind the code. **`interrupt_count` is 16 bits and wraps every 65536 edges** — 262 s at 250 SPS, 4.1 s at 16 kSPS — so any sample-loss comparison must be a sum of short windows scaled to the ODR, never one subtraction; the plan's own Phase 5 had it wrong before the driver was read. **`mcp2210_command()` never checks the echoed command byte**, and a late reply arriving after an `-ETIMEDOUT` is consumed by the *next* command, which together turn a timed-out `GET_INT_COUNT` into arbitrary bytes copied into the sample stream with the `FrameHeader` CRC computed over them afterwards — the fix is a few lines (compare `rxbuf[0]` with `txbuf[0]`, drop a mismatch instead of completing) and it is worth doing before a bench session rather than during one. Both are *read in the source and not observed*, exactly like the `hid-generic` claim, and stay debt until a test sees them. The transferable half: **§13.1's distinction between logic and offsets** — a unit test written from the same reading of the datasheet that wrote the code proves consistency, not correctness, so offset checks only become evidence with independently sourced vectors (the datasheet's own worked examples, the GPLv2 third-party driver used as an oracle rather than a dependency, or a USB analyser capture), while the fragmentation, stall-bound and `-EMSGSIZE` logic is testable today with none.

`docs/implementation_plan_mcp2210.md` is the eighth plan and **nothing in it has been executed** — it is what stands between the USB bridge's driver and both "it works" and "it can be posted to `linux-input`", and it takes `drivers/hid/hid-mcp2221.c`, the I²C sibling of the same chip family already in mainline, as the operational definition of "the standard". Its §2 is the part to read first: eight patterns that driver establishes, with the line of each, and where `hid-mcp2210.c` stands against them. The one that pays for itself immediately is that **`mcp2221_raw_event()` dispatches on `data[0]`** (`hid-mcp2221.c:760`) — a `switch` with one case per command — which is exactly the response-correlation check this file already records as debt, solved in mainline, and the protocol guarantees the echo on *every* reply including an unsupported command (§3.6.2). The one that authorises our shape is that the sibling registers an `i2c_adapter`, a `gpiochip` **and** an IIO device in one HID module, each under `IS_REACHABLE` — so "why does a HID driver register a `spi_controller` and a `gpiochip`?" has a mainline answer in the same directory since 2020.

Six defects came out of reading that driver against `docs/Register_Map_MCP2210.md`, all by inspection and none observed, and three of them are the reason the bridge cannot be measured yet. **The interrupt counter does the opposite of what it says**: Table 3-56 makes byte 1 `0x00` mean "read *and reset*", so `interrupt_count` (which writes 0, under a seven-line comment explaining that it must not reset) zeroes the counter on every read while `interrupt_count_reset` (which writes 1) does nothing — which destroys the only sample-loss measurement this link has, silently, because the numbers stay plausible. **Nothing designates the chip select pin**: §1.3.2's factory default is GP1 and the module's default is GP0, so with virgin NVRAM the CS is never asserted and the symptom is a transfer that "works" and returns garbage — the worst symptom available, because there is no error to chase. **And there is no recovery path**: `0x11`, `0x10` and `0x41` are defined and never emitted, so when the stall bound trips the bridge is left mid-transaction, and Figure 3-13 says a `0x40` with a transfer ongoing is refused — one `-ETIMEDOUT` wedges the controller permanently, and the constant that undoes it is already on line 79. The fourth is worth knowing before touching a hat: the `0x21` the probe sends to enable edge counting **zeroes bytes 13–16**, the GPIO default value and direction, so it drives every GPIO low as an output — on a board with an active-low `RESET` that is the probe holding the converter in reset.

Four things in that plan bind other work. **`checkpatch --strict` is 0 errors, 0 warnings, 0 checks on those 863 lines** — a driver with a reversed command bit scores exactly what a correct one scores, which is "measuring state is not measuring function" applied to a style tool. **`Register_Map_MCP2210.md` is a partial transcription**: Tables 3-62 and 3-63 are missing, and they are precisely the two that would define the `0x10` and `0x30` SPI-engine status codes the driver has mismatched against Table 3-60 — so that defect is not resolvable from the document, only from the datasheet, and extracting the missing tables is a Phase 0 prerequisite. **The driver exists in two copies** (`linux-med/drivers/hid/hid-mcp2210.c` and `meta-med-afe-ads1299/recipes-kernel/mcp2210/files/mcp2210-spi.c`) that already diverge in one line, `MODULE_AUTHOR` — the same problem `ti-ads1299` already solved by moving into the kernel tree with `CONFIG_TI_ADS1299=m` in the BSP fragment, and §8 is the five-step repeat of that, including what must survive the deleted recipe (the `KERNEL_MODULE_AUTOLOAD` and its `hid_generic_match()` reasoning). And two mainline items are decisions rather than tasks: the four module parameters describe the board's topology, which does not pass review and whose canonical replacement (`spi_board_info.swnode`) exists in the 6.6 tree — note the consequence for rule 9, since a generic `spi_controller` in `drivers/hid/` cannot carry `spi_device = "ads1299"` as a default — and the two sysfs attributes are a new ABI whose likely objection is strong, because counting edges on a pin is what `drivers/counter/` is for (`devm_counter_add()` is in 6.6, and `interrupt-cnt.c` is a near-identical precedent), and moving there settles the ABI, the mandatory `Documentation/ABI/` entry and the 16-bit wrap at once.

`docs/PLANO_TCC.md` and `docs/PROPOSTA_TCC.md` are the execution plan and the proposal for the thesis itself, and `docs/LAYER_MED_{BSP,DISTRO,FRAMEWORK,APP}.md` document one layer each in detail — read the relevant one before a non-trivial change to that layer.

`docs/PROJECT_CONTEXT.md` is the authoritative, up-to-date architectural reference for this repo — read it before making non-trivial changes. The remaining `docs/implementation_plan*.md` (`implementation_plan.md`, `implementation_plan_EEG.md`, `implementation_plan_improvements.md`) are earlier design iterations (Portuguese; some use an older `produto`/`meta-produto-*` naming scheme that was superseded by the current `med`/`meta-med-*` naming with a 4-layer, not 2-layer, custom stack — `meta-med-bsp` is newer than all of them) — treat them as historical design rationale, not current spec.

**Current state**: the four `meta-med-*` layers plus the `meta-med-afe-ads1299` adjunct layer are implemented (distro policy, kernel fragment, RAUC/LUKS config, the MedFramework C++ library, both EEG applications, packagegroups and images), and **the QEMU profile builds green** — `make qemu` completed all 4954 tasks on 2026-08-16, producing `med-image-eeg-qemux86-64.rootfs.ext4` (209 packages) in `build/tmp-glibc/deploy/images/qemux86-64/`. The bitbake metadata is therefore no longer unverified: recipe syntax, layer resolution and the package split all hold for `qemux86-64`. The image manifest carries `eeg-acquisition-service`, `eeg-hmi-gui`, `libmedframework1` and all four `packagegroup-med-*`.

Validated on the host toolchain (independently of bitbake):

- all 7 MedFramework translation units compile clean under `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`;
- a functional test of `MedicalConfiguration`, `MedicalStorage`, `MedicalDevice` and `MedicalLogger` (55 checks) passes;
- `eeg-acquisition-service` builds, runs, publishes CRC-valid frames to an IPC client, writes session records, and refuses to start on a tampered config or an out-of-range safety parameter.

The three risks this file used to flag are all resolved, and the resolutions are worth keeping:

1. meta-rauc ships `rauc-conf.bb` **unversioned**, so `rauc-conf_%.bbappend` was dangling — a hard parse error. The bbappend is now `rauc-conf.bbappend` (no `_%`).
2. The `meta-qt6` branch `6.8` pin in `kas-base.yml` is good; it builds Qt 6.8.4.
3. `qtbase-plugins` and `qtdeclarative-qmlplugins` do exist — `qt6.inc` declares them via `PACKAGE_BEFORE_PN` with `ALLOW_EMPTY`. Both are installed in the image.

Also learned from that first build: **a QML application recipe needs `qtdeclarative-native` in `DEPENDS`**. `qt6-cmake.bbclass` only prepends `qtbase-native` and aims `QT_HOST_PATH` at it, so without that dep the target `Qt6QmlConfig.cmake` finds no `Qt6QmlTools`/`Qt6QuickTools` (`qmlcachegen`, `qmltyperegistrar`, `qmlimportscanner`) and `find_package(Qt6 ... Qml)` fails at `do_configure`. It is a build-time host-tool dep, so it does not count against rule 6 below. Having target `qtdeclarative` in `DEPENDS` does not substitute for it.

The **STM32MP257 profile now builds green too** — `make stm32` completed all 5364 tasks on 2026-08-17, producing `med-image-eeg-stm32mp25-disco.rootfs.wic` (2.57 GiB) for `MACHINE=stm32mp25-disco`. The same recipes, the same applications and the same framework cross-compile for aarch64/cortexa35, which is the portability claim the thesis makes, now with a second machine behind it.

Getting there cost one defect worth remembering, because it is the same shape as the `WKS_FILE ?=` one below: **meta-st-stm32mp does not set `WKS_FILE`**. Its machine conf sets `WKS_FILE_DEPENDS` and leaves `#WKS_FILE += "${OPTEE_WIC_FILE}"` commented out, shipping `wic/sdcard-stm32mp257f-dk-optee-example.wks.in` as an example to copy — so `med-partitions.wks`'s claim that "vendor BSPs that need TF-A/U-Boot at fixed offsets ship their own `WKS_FILE`" was false, the distro default won by forfeit, and `do_image_wic` tried to build an EFI/GRUB ESP for a board with no ESP. It failed on `install: cannot stat '.../Image.gz'` (meta-st deploys the kernel under `${DEPLOY_DIR_IMAGE}/kernel/`), which named the kernel and not the layout — the symptom was three steps from the cause. The fix is `meta-med-bsp/wic/med-partitions-stm32mp2.wks.in`, and it was verified by dumping the GPT of the produced `.wic`, not by the green build: 11 partitions, both slots exactly 1 GiB, `med-root-a`'s PARTUUID equal to the `root=PARTUUID=` the BSP's generated `extlinux.conf` names, `med-data` carrying the pristine `ext4`/`med-data` label the provisioning safeguard keys on, and the TF-A/FIP magic bytes at the offsets the ROM code searches.

That fix first landed in `meta-med-distro/wic/`, which was wrong and is worth recording as such: it put a board name in the OS policy layer. The audit that followed found the boundary had already been crossed twice (`med-partitions.wks` naming `grub-efi`, `med-image-base.bb` naming `/dev/vda2`), which is why `meta-med-bsp` now exists and why both of those moved into it. Revalidated after the move, not assumed: `make qemu` green, `make check` 21/21, `make stm32` green with `do_image_wic` passing again, the QEMU GPT byte-identical to before the rename, `bitbake -p` clean with zero warnings, and `MED_WKS_FILE` resolving per machine from the new layer (`bitbake -e | grep ^WKS_FILE=`). The precedence claim in that layer's comments was fault-injected rather than reasoned about: `MED_WKS_FILE = ""` from a KAS fragment does override the layer default and does trip the build-time guard, which is what proves the two-step `_DEFAULT` indirection was necessary.

**The STM32MP257F-DK has now booted** — 2026-08-18, `make stm32 KEY=development`, recorded in `BRINGUP_STM32MP2.md` §9 and measured in `RESULTS.md` §8. What that boot established: the TF-A/OP-TEE/U-Boot chain works and slot A boots from the PARTUUID the `.wks` fixes; `/data` is a real LUKS2 volume provisioned on first boot in 13 s, with the key at `root:root 0400` on `med-boot` (the ext4-vs-vfat argument, finally measured); RAUC enumerates both slots and identifies the booted one; the journal's Forward Secure Sealing validates; and the ST GPU no longer panics the secure world, because the etnaviv-vs-galcore hypothesis held.

**The A/B update path now runs on the board** — 2026-08-30, `BRINGUP_STM32MP2.md` §9.10 and `RESULTS.md` §8. `rauc install` verifies a signed verity bundle against the device keyring, writes the inactive slot (confirmed byte-for-byte: the partition's first 747,560,960 bytes hash to the manifest's checksum), and reorders the bootloader environment to `BOOT_ORDER=B A` — keeping the previous slot as fallback rather than replacing it. Two defects had to be found first, both invisible to every build. `med-kernel-features.cfg` never required `CONFIG_DM_VERITY` although the distro mandates verity bundles: `linux-yocto`'s defconfig sets it and `linux-stm32mp`'s does not, so QEMU passed by inheriting a vendor default and the board would have failed at `DM_TABLE_LOAD`. And **nobody writes `BOOT_ORDER` at provisioning time** — the `.wks` creates `u-boot-env` empty, RAUC writes that variable only during an install, and `rauc status mark-good` writes only `BOOT_<slot>_LEFT` — so a freshly flashed device reports every slot `bad`, including the one it is running from, and `Activated: none`. That second one is still open; its fix is the same U-Boot script that owes `rauc.slot=` on the cmdline and the actual slot switch. Until that script exists, `BOOT_ORDER` is written and never read: say "write and activate are validated on hardware, the slot switch is not".

`docs/BOOT_SLOT_AB_STM32MP2.md` is where slot selection now lives — the manual bench experiment that booted the written slot (edit `extlinux.conf`'s `root=PARTUUID=`, reboot, `Booted from: rootfs.1`), the specification for the `bootcmd` that replaces it, and four findings that came out of having a second rootfs rather than out of booting. Two of those bind other work and neither has a fix: **each slot has its own machine identity** (the rootfs ships no SSH host key and a 0-byte `/etc/machine-id`, so every slot generates its own on first boot — an A/B update changes the device's SSH host key, observed), and **the audit trail lives inside an A/B slot** (`Storage=persistent` writes `/var/log/journal/<machine-id>/` on the rootfs, so the next update destroys one of the two histories and the FSS seal is per-slot) — the same hazard `implementation_plan_luks.md` already solved for the `/data` key, repeated for the IEC 62304 evidence. Two more are prerequisites for the script itself: `med-root-b` has no fixed `--uuid` in the `.wks` (wic randomises it per build, so no `root=PARTUUID=` for slot B is stable), and `med-boot` is shared, so the A/B path delivers a rootfs and never a kernel.

Three things that boot left open or newly broken, and they are the current work queue: **`weston.service` fails** with `status=1` and takes the HMI with it, on a board whose DRM did come up; **the acquisition service may be restarting** (two `Started` lines in the boot log, `NRestarts` never consulted); and **the board has no initialised RTC**, so every record `MedicalLogger`/`MedicalStorage` writes carries a wrong timestamp — a traceability problem nothing in the repo addresses.

Two facts from that boot bind future work. `/dev/disk/by-partlabel/` is one flat namespace across every disk, and this board's factory eMMC carries the same names the ST layout uses — so `u-boot-env` must be addressed by PARTUUID, never by partlabel. And `mmcblk0`/`mmcblk2` swapped roles between two boots of the same hardware with no configuration change: device numbering is a race, so no `/dev/mmcblkNpM` path belongs anywhere in this repository, not even in a comment.

Still unbuilt or unvalidated: the Tomograph profile (`make tomograph`), `med-image-prod`, and the `rpmsg` path (the Cortex-M33 is present and available, but carries no firmware — and the board reports `Support of signed firmware only`, a constraint the AFE plans now account for). Boot-slot selection is **no longer** on this list — see `implementation_plan_uboot_ab.md`. And the acquisition service **crash-loops on the board** for the same reason the `rpmsg` path is unvalidated: `MED_EEG_DRIVER = "rpmsg"` with no firmware means `RpmsgDevice::selfTest()` cannot open the endpoint, so the service exits 1 and restarts. Measured: 163 restarts, a period of exactly 2.500 s, ~280 ms of life per attempt. Nothing stops it — neither unit declares `StartLimitBurst`/`StartLimitIntervalSec`, and with `RestartSec=2s` the cadence sits just outside systemd's default 5-starts-in-10s window, so the unit **never reaches `failed`** and `systemctl list-units --state=failed` reports nothing. A unit skipped by a `Condition*` behaves the same way: it does not fail, it disappears.

## Build Commands

There is no local toolchain beyond `kas` — all builds run through it, which clones `poky`, `meta-openembedded`, `meta-rauc`, etc. into `layers/` on first run (network access required; outputs are gitignored).

**Prefer the `Makefile`**: it runs the same builds inside the pinned upstream kas container (`ghcr.io/siemens/kas/kas:5.2`), which is how the build host itself stays reproducible. `make help` lists the targets; `make risks` (parse-only, seconds) is the right first command on a fresh clone, and `make framework` / `make service` are the cheap inner loops. Append `NATIVE=1` to any target to use the host's own kas instead — both modes share `downloads/` and `sstate-cache/`. `docs/BUILD_CONTAINER.md` covers the setup and its measured limits (notably: no X11 reaches the container under snap-packaged Docker, so the Qt HMI must be exercised with `NATIVE=1`).

The raw kas commands below still work and are what the Makefile targets wrap:

```bash
# Build the EEG PoC image for QEMU (fast inner-loop target, no hardware needed)
kas build kas/project-eeg-qemu.yml

# Build the EEG PoC image for the STM32MP257 physical target
kas build kas/project-eeg-stm32mp2.yml

# Build the Tomograph profile (architecture reuse/portability validation)
kas build kas/project-tomograph.yml

# Boot the QEMU build
kas shell kas/project-eeg-qemu.yml -c "runqemu qemux86-64 nographic"

# Inspect layer setup / priorities (parse-only sanity check, doesn't build)
kas shell kas/kas-base.yml -c "bitbake-layers show-layers"

# Verify a kernel config fragment made it into the build for the active target
kas shell kas/project-eeg-qemu.yml -c "bitbake -e virtual/kernel | grep ^SRC_URI="

# Fast inner loop: build the acquisition path alone, never compiling Qt.
# (`kas build` has no --extra-conf option — building the recipes directly is
# the way to skip the image, and `make framework` / `make service` wrap these.)
kas shell kas/project-eeg-qemu.yml -c "bitbake med-framework-api"
kas shell kas/project-eeg-qemu.yml -c "bitbake eeg-acquisition-service"
```

Each `kas/project-*.yml` is a standalone entrypoint that includes `kas/kas-base.yml` and sets its own `machine:`, `target:` and the `MED_EEG_*` variables that select the acquisition backend. `kas-project.yml` at the repo root is a thin alias for `kas/project-eeg-qemu.yml`.

The **application's** hardware adaptation surface is one variable: `MED_EEG_DRIVER` (`simulated` on QEMU, `rpmsg` on the STM32MP257) is substituted into `/etc/medplatform/eeg.conf` at build time. No application source differs between the two targets — that is what the portability metric measures, and it is the claim to make.

Do not extend that sentence to the platform: **the platform's adaptation surface is seven variables, one layer, and one adjunct layer per analogue front-end.** `MED_EEG_DRIVER`, `MED_EEG_ADDRESS`, `MED_EEG_LINK`, `MED_EEG_REQUIRE_ENCRYPTION`, `MED_BOOTLOADER` and `MED_DATA_KEY_SOURCE` are set per target in the KAS project files, `MED_WKS_FILE` is answered per machine by `meta-med-bsp`, that layer is where any further board fact goes, and a front-end's kernel code goes in an adjunct layer outside the stack. This file used to claim "the hardware adaptation surface is deliberately one variable" flatly, which was false by four variables, and then "five variables plus one layer", which the front-end work made false by two more — a thesis claim, so worth restating each time rather than rounding down. A consequence worth stating too: because those values live in KAS YAML rather than in a layer, the layer stack alone does not build a working STM32 image, and `kas` is load-bearing metadata rather than only an orchestrator.

## Architecture: the 4-layer `MedStack`

Strict, unidirectional dependency chain — upper layers consume lower layers only through abstract APIs; lower layers never depend on upper layers:

```
meta-med-app        (priority 10) — business logic, HMI GUI, device profiles/images
        │  consumes MedFramework C++ APIs only
        ▼
meta-med-framework   (priority 9)  — MedFramework: C++ abstraction over OS/HW
        │  POSIX, D-Bus, systemd, cgroups
        ▼
meta-med-distro      (priority 8)  — MedOS: distro policy, security hardening
        │  selects a disk layout and a bootloader by variable, names neither
        ▼
meta-med-bsp         (priority 7)  — board adaptation: disk layouts, boot path
        │  drivers, DTS, TF-A, U-Boot/GRUB
        ▼
vendor BSP layer     (priority 6)  — meta-st-stm32mp, meta-yocto-bsp

    meta-med-afe-ads1299 (priority 7)  — ADJUNCT, not a fifth layer: the kernel
                                         code of one analogue front-end. Fills
                                         MED_BSP_INSTALL, consumes nothing.
```

**`meta-med-bsp` is the only custom layer allowed to name a machine, a bootloader or a device node.** That restriction is what makes the reuse claim countable: a new board adds files there and changes nothing above it. The split it enforces is *policy vs. placement* — "two identically-sized slots called med-root-a/med-root-b, and /data is not one of them" is policy and lives in `meta-med-distro`; "TF-A starts at 17 KiB, GRUB reads the ESP, the kernel gets `console=ttyS0`" is placement and lives here. The layer exists because that line was crossed twice without failing a build: `med-partitions.wks` hardcoded `loader=grub-efi` behind a generic filename in the OS policy layer, and `med-image-base.bb` carried `QB_KERNEL_ROOT = "/dev/vda2"` — a virtio path plus a partition index from one particular disk — in a recipe whose own description calls it device-class agnostic. Neither surfaced until a second machine needed a different answer.

- **`meta-med-distro`** (`meta-custom/meta-med-distro/`): OS policy layer. `conf/distro/med-os.conf` sets `INIT_MANAGER = "systemd"`, `usrmerge`, `rauc`. Security/compliance surface: read-only rootfs, RAUC A/B OTA, LUKS, PAM. Kernel policy is injected via the **wildcard** `recipes-kernel/linux/linux-%.bbappend` so distro-level kernel requirements (cgroups, OverlayFS, OpenAMP/rpmsg) apply automatically regardless of which vendor kernel (`linux-yocto`, `linux-st`, etc.) is in use — never target a specific `linux-<vendor>_%.bbappend` here. It has **no `wic/` directory**: `med-os.conf` does `WKS_FILE = "${MED_WKS_FILE}"` (hard `=`, so no machine conf can take it back — poky's `qemux86-64.conf:41` sets `WKS_FILE ?=`) and never names a layout.

- **`meta-med-bsp`** (`meta-custom/meta-med-bsp/`): board adaptation, and today it is `conf/layer.conf` plus two disk layouts — `wic/med-partitions-efi.wks` (GPT dual-boot A/B with encrypted `/data`, for GRUB/EFI machines; this is the file formerly known as `meta-med-distro/wic/med-partitions.wks`) and `wic/med-partitions-stm32mp2.wks.in` (the same A/B policy over the TF-A/FIP/`u-boot-env` chain the STM32MP2 ROM code requires). Selection is a machine override on `MED_WKS_FILE_DEFAULT`, then `MED_WKS_FILE ?= "${MED_WKS_FILE_DEFAULT}"` — the two-step matters, because a bare `MED_WKS_FILE:qemux86-64 =` would beat the unsuffixed assignment a KAS project file makes and silently win over it. `LAYERDEPENDS` is `core` only, and there must never be a bbappend here onto a recipe from a higher layer: this layer provides and does not consume.

- **`meta-med-afe-ads1299`** (`meta-custom/meta-med-afe-ads1299/`): the adjunct layer, and the only place in this repository outside the Cortex-M33 firmware where a converter's part number may appear. It holds `ti-ads1299` (an IIO driver derived from mainline's `ti-ads1298.c`), `mcp2210-spi` (a HID driver that registers a USB bridge as a real `spi_controller`, plus its gpiochip and the GP6 edge counter), the udev rule that gives the converter a name instead of a probe-order number, and the hat's devicetree overlay. It is priority 7 like `meta-med-bsp`, declares `LAYERDEPENDS = "core"` only, and provides without consuming. Which of its contents an image gets is decided by `MED_EEG_LINK`: `usb` installs both modules and the udev rule, `spi` installs the AFE driver alone, `amp` and `simulated` install nothing — so the product profile carries the layer and none of its code. Both module recipes carry a `do_check_kernel_config` task that fails the build when the kernel lacks a symbol they need, which is how the fragment in `meta-med-distro` stays checkable rather than aspirational. **Do not count this as a fifth `MedStack` layer** and do not include it in the reuse metric.

- **`meta-med-framework`** (`meta-custom/meta-med-framework/`): `med-framework-api` provides 6 standardized C++ abstraction headers apps must use instead of touching the OS/kernel directly:
  - `MedicalIPC` — OpenAMP `rpmsg` inter-core comms (Cortex-A35 ↔ Cortex-M4) + local IPC sockets
  - `MedicalLogger` — structured, tamper-evident audit logging to `systemd-journald` (IEC 62304 / FDA traceability)
  - `MedicalStorage` — secure persistence to encrypted `/data`
  - `MedicalUpdate` — D-Bus client wrapper around the RAUC OTA daemon
  - `MedicalConfiguration` — calibration tables, operational thresholds, DERS safety-parameter checks
  - `MedicalDevice` — universal sensor/actuator abstraction (AFEs, ADCs)

  Implementation notes: the library is one shared object (`libmedframework.so`, CMake, C++17) whose only external dependencies are `libsystemd` (sd-journal, sd-bus) and `libcrypto` (SHA-256) — everything else is POSIX, which is why it builds unchanged for both targets. `MedicalTypes.h` carries the shared `Status`/`Result<T>` vocabulary; `MedicalDevice.h` also defines the `med::amp::FrameHeader` wire format used both by the rpmsg link and by the service→HMI socket, and `med::amp::ControlMessage`/`ControlAck`, the fixed-layout messages that carry front-end settings to a producer and require an answer (an option the producer does not understand is a refusal, never a silent drop). Built-in device drivers: `simulated`, `rpmsg` and `iio`. Every driver is named after a **transport**, never after a part; a driver named after a converter would end the portability claim the `grep` in `implementation_plan_ads1299.md` §3 checks.

- **`meta-med-app`** (`meta-custom/meta-med-app/`): pure userspace. Apps: `eeg-acquisition-service` (data daemon, uses `MedicalIPC`/`MedicalLogger`), `eeg-hmi-gui` (Qt6 Quick/Wayland UI). Packagegroups hold **platform capability only, never applications** — `packagegroup-med-core` (framework runtime), `packagegroup-med-amp` (AMP enablement + BSP firmware hook via `MED_AMP_FIRMWARE`), `packagegroup-med-gui` (weston + Qt, no app). Images install the apps: `med-image-eeg.bb`, `med-image-tomograph.bb`, both `require recipes-core/images/med-image-base.bb` across the layer boundary.

- **`kas/`**: `kas-base.yml` is the single source of truth for external repo deps (`poky`, `meta-openembedded`, `meta-rauc`, `meta-qt6`) and the four `meta-med-*` layer paths, plus `local_conf_header` (package format, sstate/downloads dirs, buildstats). Per-target files (`project-eeg-qemu.yml`, `project-eeg-stm32mp2.yml`, `project-tomograph.yml`) set `machine:`, `target:`, the `MED_EEG_*` variables, and any hardware-specific repo (e.g. `meta-st-stm32mp` for the STM32 target). `debug-tweaks` is deliberately *not* set globally — dev images request it themselves so `med-image-prod` stays hardened.

## Rules when editing this codebase

1. **No layer-boundary bleeding**: never put application logic in `meta-med-distro`, and never put BSP/hardware drivers in `meta-med-app` or `meta-med-framework`. Apps must call `Medical*.h` APIs from the framework layer, never raw sysfs/devfs or BSP drivers directly. **A machine name, a bootloader name, a partition offset or a device node (`/dev/vda2`, `mmcblk`, `ttyS0`, `by-partlabel/esp`) appears only in `meta-med-bsp`** — anywhere above it, that is the bug, and note that no build will report it. Both times this rule was broken, the mechanism was a generic-looking name over machine-specific content; when a value differs per board, add it to `meta-med-bsp` keyed by machine override rather than defaulting it upstack. **The `MedStack` is four layers, and it stays four.** Hardware enablement that belongs to one particular front-end (out-of-tree kernel drivers, a devicetree overlay for one AFE) goes into an *adjunct* layer outside the stack — see `implementation_plan_iio_afe.md` §4 — which provides and never consumes, exactly like `meta-med-bsp`. Adjunct layers are deliberately excluded from the reuse metric; do not count them as a fifth layer.
2. **Scarthgap compatibility**: every `conf/layer.conf` must declare `LAYERSERIES_COMPAT_<collection> = "scarthgap"`. Use modern override syntax (`:`, e.g. `IMAGE_INSTALL:append`), not the legacy `_` syntax.
3. **Kernel changes** belong in `meta-med-distro/recipes-kernel/linux/linux-%.bbappend` (wildcard, not a vendor-specific bbappend) so they stay portable across BSPs. A capability the layers above assume must be *written down* in `med-kernel-features.cfg` even when both current kernels happen to have it — this trap has now been sprung three times. `CONFIG_DM_VERITY` was missing and `linux-yocto`'s defconfig hid it while the board would have failed; `CONFIG_SPI`, `CONFIG_GPIOLIB` and `CONFIG_IIO_KFIFO_BUF` were missing with the roles reversed, present from ST's defconfig and absent on QEMU. And note the limit of the mechanism: `CONFIG_REGMAP` has no Kconfig prompt, so a fragment cannot turn it on at all — it is *selected* by drivers. Where a fragment cannot guarantee, detect: the AFE module recipes fail the build on a missing symbol, and that guard was fault-injected against both real `.config` files before being believed.
4. Do not commit build outputs (`build/`, `layers/`, `downloads/`, `sstate-cache/`, `.kas/`) — already covered by `.gitignore`.
5. Security features (read-only rootfs, RAUC A/B, audit logging, LUKS) exist to satisfy IEC 62304 software-partitioning/traceability requirements — treat them as architectural constraints, not optional hardening.
6. **Applications never gain a second dependency.** `eeg-acquisition-service` and `eeg-hmi-gui` link `medframework` and (for the HMI) Qt, and nothing else. If a new feature seems to need a system library in an app recipe's `DEPENDS`, the feature belongs behind a framework API instead — that constraint is the thesis, not a style rule. **The framework's own two dependencies are under the same rule**: the `iio` driver was written against `open`/`read`/`poll` and sysfs text files rather than against `libiio`, deliberately, because "this library needs `libsystemd` and `libcrypto` and nothing else" is a claim the thesis makes and a third entry would end it.
7. **`linux-%` also matches non-kernels** (`linux-libc-headers`, `linux-firmware`). The bbappend guards on `bb.data.inherits_class('kernel', d)`; keep that guard when extending it.
8. **Config stores are sealed at build time.** `MedicalConfiguration` refuses to load a store without a matching `.sha256` sidecar, so any recipe shipping one must generate the sidecar after substituting variables (see `do_seal_configuration` in `eeg-acquisition-service_1.0.0.bb`).

9. **A part number is contained, and the containment is a `grep`.** `ADS1299` and `MCP2210` appear in `meta-med-afe-ads1299`, in the M33 firmware and in the design documents, and nowhere else. `grep -rni 'ads1299\|mcp2210' meta-custom/meta-med-{app,framework,bsp}` returns nothing at all; in `meta-med-distro` the only hits are the name of a plan document and the name of the adjunct layer, neither of which is a fact about a part. Comments are included in that discipline on purpose — a comment explaining "what an ADS1299 does" in the framework is the first step towards a field named after one. Say "a converter of this class" instead. **And the grep is necessary, not sufficient**: on 2026-09-16 the framework passed it while being an EEG framework anyway — it parsed `afe.gain`/`afe.reference_uv`/`afe.lead_off_detection`/`afe.bias_drive`/`afe.test_signal` in all three drivers and refused every other key, its simulator carried the converter's `VREF/2400` generator and `f_CLK/2^21` rate, and the `iio` driver's self test wrote the kernel driver's private attributes and judged the answer by datasheet numbers. Constants and a vocabulary leak without a part number. Now each driver owns the vocabulary of its **transport** only (`simulated`: its generator's parameters; `rpmsg`: none, forwarded to the producer; `iio`: sysfs attribute names), the application's `afe.*` prescription is translated per link at build time by `do_derive_device_options` in the service recipe, and the analogue self test runs in the kernel driver at probe — a front-end that fails it is never registered.
